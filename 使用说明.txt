【日常：什么都不用做】
  GitHub Actions 每天北京时间 09:17 自动为三个账号
  （手机号尾号 4060 / 7100 / 6717）各模拟一次桌面端登录动作，
  当天 300 积分随之入账。不开电脑、不打开客户端、不用点任何按钮。
  账号密码已存在各自专属的加密 Secret 里，云端每天现取新会话，
  所以客户端切号、退出登录、30 天令牌到期都不会影响签到。

  成功默认不推企业微信（不打扰）。想确认有没有跑：
  打开 https://github.com/caiping527/raccoon-checkin/actions 看是否全绿。
  想每次成功都收到推送：把仓库变量 SUCCESS_NOTIFY 设为 1。

【唯一本机工具：密码登录.bat】
  只有这两种情况才需要双击它：
    1. 新增一个账号
    2. 该账号改了密码
  输入该账号的 11 位手机号 + 密码，问题「是否把密码存入云端」
  直接回车选 Y。看到【成功】即可关窗口。
  有几个账号就各跑一次；已登记过的不用重复跑，重复跑也无害。
  工具会自动识别手机号尾号、自动加回云端账号列表，
  不需要手改任何文件。

  密码默认明文显示便于核对；想隐藏：
  命令行运行 python password_login.py --hide-password

【关于积分和「过期数据」】
  程序判成功只看一件事：**今天的积分账本里有没有新入账 300**
  （按 daily_grant 记录的 created_at 日期严格比对今天）。
  不会把 7 天前的旧记录当成今天成功，也不会拿历史余额冒充当日入账。
  消息里那句「账本有效期字段至 2026-11-15（仅记录）」只是账本
  自带字段，程序只记录、不拿它判成败。

  你查到的「积分保留 7 天」和「300 不过期」并不矛盾，
  更可能是：每天新发的 300 各自保留 7 天，余额是滚动 7 天窗口。
  想自己确认：连着几天看 Actions 运行摘要里的
  balance.daily_points / available_points，
  若涨到约 2100（7×300）后稳定，就是 7 天滚动。

  ★ 不建议改成「每 7 天登一次」或「每 7 天轮一个号」：
    · 积分按账号独立，别的号登了不会给这个号加分
    · 少登一天就少一天的新 300，滚动余额反而变少
    · 云端每天跑只是几次只读请求，零成本、不开电脑、
      不打断桌面端正在跑的任务，没有可省的东西
    · 判据要求「今天入账」，降频会导致没登的那天被判失败并推告警

【常见失败】
  · 401 会话已撤销 → 该账号没登记过密码登录，或密码改了；
    双击「密码登录.bat」重跑该账号即可
  · HTTP 400 iam_confirm_required → 新版已自动处理（云端登录后
    先 POST /api/web/auth/v1/iam/confirm 确认会话），无需人工干预
  · 网络超时 / HTTP 5xx → 云端到小浣熊偶发抖动，已自动重试 2 次；
    仍失败时企微会写明「云端网络波动」，不影响下次定时
  · bat 一闪而过 → 已修复（纯 ASCII + CRLF + pause）；
    若仍出现，在该目录打开 cmd 手动敲 bat 名看报错
  · 提示「密码登录失败：HTTP 200 OK」→ 旧版解析 bug，已修复。
    密码错会返回 401，所以 200 OK 代表密码是对的
  · 缺少 GH_TOKEN → 把 GitHub 令牌设为系统环境变量
  · 凭据归属不符 → 该环境的令牌属于另一个号，重新登记正确账号

【安全边界】
  · 密码只在本机内存出现，传给 gh 一律走 stdin，不落盘、不打印
  · 选 Y 后密码存 GitHub 加密 Secret，不进代码、不进日志、不进推送
  · 仓库保持 Private；公开仓库 60 天无活动会被 GitHub 停用定时任务
  · 请仅用于自己的账号，并遵守平台服务条款
  · 若曾在聊天/截图里明文发过密码，建议去官网改一次密码，
    再对那个账号重跑一次「密码登录.bat」
